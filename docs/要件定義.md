# 要件定義

## 1. 背景

外食・中食で食べたものを写真に撮っているが、カメラロールに埋もれて探せない。
その結果、以下のような場面で困っている。


| 場面        | 困っていること                      |
| --------- | ---------------------------- |
| 行きつけの洋食屋  | 毎回違うメニューを頼みたいが、どれを食べたか思い出せない |
| コンビニのスイーツ | 新発売を選びたいが、似たものを前に食べたか判断できない  |
| スターバックス   | カスタムして注文するが、前回のカスタム内容を再現できない |
| ケーキ屋の季節限定 | 去年も食べたのか、そのとき美味しかったのかが分からない  |


## 2. 目的

**いろんな味を楽しむこと。**

同じものばかりにならないように、食べたものを記録し、
「これは前に食べた」がすぐ分かる状態をつくる。

## 3. 解決したい課題

> 「これ、前に食べたっけ？ そのときどうだった？」が思い出せない

このアプリの本体は記録機能ではなく、**店の前・棚の前で3秒で引ける検索**である。

## 4. ターゲットユーザー

- 外食・中食が好きで、食べたものを写真に撮る習慣がある人
- 同じ店で違うメニューを試したい、新商品を選びたいという志向がある人
- 写真は撮るが整理はしない人



## 5. 機能要件



### 5.1 MVP（初回リリースに含む）

| # | 機能 | 内容 |
|---|---|---|
| 1 | ログイン | Google アカウントでのログイン（Supabase Auth） |
| 2 | 記録の登録 | 写真（**商品は最大5枚**、あわせて登録する**メニュー・店の写真は最大10枚**。1枚ごとに商品／メニュー／店を指定し、既定は商品。メニューと店は `shop_photos` に保存される）・食べた日・店・商品・評価（★1-5）・感想・価格（任意）・カスタム内容。商品を新規登録する場合は、分類（`categories`。**必須**）と季節限定かどうかもあわせて指定する |
| 3 | 記録の編集・削除 | 自分の記録のみ編集・削除できる。写真は追加・削除・並べ替えができる。削除は物理削除とし、写真（複数枚）・いいね・コメントも同時に削除する |
| 4 | 記録の一覧 | 写真グリッドで新しい順に表示する。写真の上に店名・商品名・評価・日付を重ねる。上部で分類（`categories`）と業態（`shop_kinds`）による絞り込みができ、2つは組み合わせて適用される。複数枚ある記録は代表写真に枚数バッジを表示する |
| 5 | 店の追加・編集 | 記録とは別に、店だけを登録できる。またメニュー写真と店の写真を追加でき、その中で店を選ぶことも新しく登録することもできる。登録済みの店は店名・業態・エリア・**閉店したかどうか**を編集できる |
| 6 | 検索 | 商品名・店名・分類で検索する。「食べたことがある」（**自分の記録**）と「まだ食べていない」（**他ユーザーの記録**にあり自分が未記録のもの）を分けて表示する |
| 7 | 店・商品の記録閲覧 | 店一覧（自分の記録がある店、または自分が写真を撮った店。**最終活動日**＝記録した日と写真を撮った日の新しいほう、の降順。**店の写真があればサムネイルとして表示**し、なければ業態の絵文字を出す）→ その店で食べた商品（回数・評価）→ その商品の記録履歴、の3階層。**回数・評価・履歴はいずれも自分の記録のみ**を対象とする。店の詳細には「他ユーザーが記録していて自分は未記録の商品」と、**その店のメニュー写真**（撮影日の新しい順）も表示する。店の写真はヘッダーに出す。どちらも店の詳細から直接追加できる |
| 8 | カレンダー表示 | 月表示。写真サムネイルの上に分類の絵文字を重ねる（4件以上は3つ＋件数）。日付を選ぶと、その日の記録を同じ画面に一覧表示する |
| 9 | タイムライン | 他ユーザーの記録を新しい順に表示する。いいね・コメントの対象を見つける入口となる |
| 10 | いいね | 他ユーザーの記録にいいねを付ける |
| 11 | コメント | 他ユーザーの記録にコメントを付ける |
| 12 | いいねした記録の一覧 | マイページから、いいねした記録を新しい順に表示する |
| 13 | 前回カスタムのコピー | 同じ商品の直近の記録からカスタム内容を引き継いで登録する |
| 14 | 表示テーマの切り替え | ライト／ダークを切り替える。初期値は端末の設定に従い、選択はブラウザ（localStorage）に保存する。端末ごとの設定とし、サーバーには保存しない |
| 15 | マスタ管理 | 分類（`categories`）・業態（`shop_kinds`）の追加。**管理者のみ** |

商品（`items`）の事前登録は行わない。記録するたびに自動的に作られる。
そのため「まだ食べていないメニュー」は、他ユーザーが記録した商品のうち自分が未記録のものを指す。
メニューの事前登録方式は、コンビニで成立しないうえ、店のメニュー改定に追従できないため採用しない。

**権限の整理**

| 操作 | 誰ができるか |
|---|---|
| 商品（`items`）を作る | 全ユーザー（記録時に自動作成） |
| 商品の分類・季節限定を設定・変更する | 全ユーザー |
| 分類・業態の種類そのものを追加する | **管理者のみ** |
| 記録・コメントの編集・削除 | 投稿者本人のみ |

**集計・表示の対象**

同じ「回数」「評価」でも、自分の記録だけを数えるのか全ユーザーを数えるのかで結果が変わるため、
画面ごとに対象を定める。

| 表示 | 対象 |
|---|---|
| 記録の一覧・カレンダー | 自分の記録のみ |
| 店一覧の品数・記録数 | 自分の記録のみ |
| 店の詳細の商品ごとの回数・評価 | 自分の記録のみ |
| 商品の記録履歴 | 自分の記録のみ |
| 検索の「食べたことがある」 | 自分の記録のみ |
| 検索・店の詳細の「まだ食べていない」 | **他ユーザーの記録**（自分が未記録のもの） |
| タイムライン | **全ユーザーの記録** |

### 5.3 主要な処理フロー

#### 初回ログイン時のユーザー登録

Supabase Auth でログインしても、MySQL の `users` には自動では作成されない。
Next.js が明示的に登録APIを呼ぶ方式とする。

1. Google でログイン（Supabase Auth）
2. Next.js の middleware が `users` の登録状況を確認
3. 未登録なら `/onboarding`（ニックネーム入力画面）へリダイレクト
4. ニックネームを入力して送信
5. `POST /api/users` で Spring Boot が `users` を作成
6. 以降は通常の画面へ

middleware が全ルートを通るため、URL を直接指定されても登録画面へ誘導される。

**アクセス制御**

`users` が存在しないリクエストは 403 を返すが、**`POST /api/users` だけは例外**とする。
このAPIはユーザーを作るためのものであり、例外にしないと初回登録が永久にできない。

| API | `users` が未登録のとき |
|---|---|
| `POST /api/users` | **許可する**（JWT が有効であれば通す） |
| それ以外 | 403 を返す |

**なりすまし・権限昇格の防止**

| 項目 | 方針 | 防ぐこと |
|---|---|---|
| `users.id` | **JWT の `sub` から決定する。** リクエストの値は使わない | 他人のIDでユーザーを作られること |
| `role` | **リクエストからは受け取らない。** サーバー側で一般ユーザーに固定する | 誰でも管理者になれること |
| 管理者の判定 | **MySQL の `users.role`** で判定する | Supabase JWT の `role`（ログイン済みを表す `authenticated`）を管理者権限と誤認すること |

**最初の管理者**

`role` を入力で受け付けないため、管理者は自動では生まれない。
自分が初回ログインしてユーザーが作成されたあと、**データベースに直接1回だけ UPDATE を実行**して管理者にする。
画面から他のユーザーを管理者にする機能は将来対応とする。

**JWT の検証項目**

署名だけでなく、以下をすべて検証する。

| 項目 | 検証しないと起きること |
|---|---|
| 署名 | 偽造されたトークンが通る |
| `iss`（発行者） | **他人の Supabase プロジェクト**が発行したトークンが通る |
| `aud`（宛先） | 別アプリ向けのトークンが使い回される |
| `exp`（有効期限） | 期限切れのトークンが通る |

Supabase は誰でも無料でプロジェクトを作れるため、`iss` の検証がないと、
攻撃者が自分のプロジェクトで発行した正しく署名されたトークンで認証を通過できてしまう。

利用者を指す識別子は、ドキュメント・実装ともに **`sub`** に統一する。

#### 店の登録フロー

店は「正規化した店名 + エリア」で一意とする（`UNIQUE (shop_name, area_id)`）。
エリアは国内では都道府県、海外では国を指す。地域（関東・東アジアなど）でグループ化して選ばせる。
チェーン店は支店名を外して登録し、同一都道府県内の別店舗で買った商品を同じ商品として扱う。

1. 選択した都道府県内の**既存の店を先にサジェスト**する
2. 見つからない場合だけ Google Places で実店舗を検索する
3. Places の住所から**都道府県を自動設定**する
4. Places から取得した店名を**初期値として表示**する
5. ユーザーが店名を確認・修正する（チェーン店は支店名を外す）
6. 保存前に正規化する（前後の空白除去、全角スペースを半角に、連続する空白を1つに）
7. 同じ店名と都道府県が既に存在する場合は、新規作成せず**既存の店を使用する**

```
Places から取得：セブンイレブン 大阪駅前店
                        ↓ 支店名を外す
登録名：セブンイレブン ／ エリア：大阪府
```

支店名を外す判断が必要なのは**最初に登録する1人だけ**で、2人目以降は手順1のサジェストから選ぶ。

**登録の入口は2つある**

| 入口 | 使う場面 |
|---|---|
| 記録の登録画面 | 食べたものを記録するとき。店が未登録なら同時に作られる |
| **店一覧の「＋ 店を追加」** | **記録はしないが、メニュー写真だけ残したいとき** |

どちらも上記の手順は同じ。店だけを先に登録した場合、記録が0件の状態で店一覧に並ぶ。

**MVP では自動判定しないもの**

- チェーン店か個人店か
- 店名のどこまでが支店名か
- 店名変更の前後で同じ店か

**受け入れる制約**

同一都道府県に同名の別店舗がある場合、手順7で自動的に統合される。
実害が出るのは「同名の別店舗が同一都道府県にあり、かつ両方を記録する」場合に限られるため、
MVP では許容する。必要になった時点で、店名に市区町村を付けて区別する（例：`パティスリー ミナミ（堺市）`）。

#### 商品名の表記ゆれ対策

商品（`items`）は `UNIQUE (shop_id, item_name)` で一意としているが、完全一致での判定のため、
表記がわずかに異なると別の商品として登録されてしまう。

特に「他ユーザーが記録していて自分は未記録の商品」の判定が壊れる（自分が食べたはずの商品が
別表記で登録されていると、未記録として表示されてしまう）ため、以下で対処する。

| 対策 | 内容 |
|---|---|
| 入力補助 | 商品名の入力中に、その店の既存商品を候補として表示する。原則として候補から選ばせ、新規登録は候補にない場合に限る |
| 正規化 | 保存前に前後の空白を除去し、全角スペースを半角に変換し、連続する空白を1つにまとめる |

店名は Google Places API の候補から選ばせることで表記ゆれを防ぐが、商品名には外部のマスタが
存在しないため、自分たちの `items` を候補として使う。

「オムライス」と「オムライス（デミグラス）」のように、人間でも同一かどうか判断が分かれるものは
防げない。商品の統合機能は MVP には含めない。

#### 写真の種類と置き場所

写真は3種類あり、種類によって保存先のテーブルと表示先が変わる。

| 種類 | 保存先 | 一覧・写真タブ | 記録の詳細 | 店一覧 | 店の詳細 |
|---|---|---|---|---|---|
| **商品** | `record_photos` | ✅ | ✅ | — | — |
| **メニュー** | `shop_photos`（`menu`） | — | — | — | ✅ 撮影日の新しい順 |
| **店** | `shop_photos`（`shopfront`） | — | — | ✅ **サムネイル** | ✅ ヘッダー |

**なぜ分けるか**

メニューと店の写真は食事の記録ではなく**店の情報**である。
「店に行ったが食べずに撮った」場合にも登録できる必要があり、記録に紐づけると成立しない。
また、記録の写真5枚の枠をこれらが消費してしまう問題も避けられる。

店一覧は業態の絵文字だけでは見分けがつきにくいため、店の写真があればサムネイルとして表示する。

**上限と圧縮の設定**

| 対象 | 上限 | 圧縮 |
|---|---|---|
| 商品の写真（`record_photos`） | **1記録あたり5枚** | WebP・長辺1200px・約150KB |
| メニュー写真（`shop_photos` / `menu`） | **1回の登録あたり10枚**。累積は無制限 | WebP・**長辺1600px**・約300KB |
| 店の写真（`shop_photos` / `shopfront`） | **1人1店舗につき1枚** | WebP・長辺1600px・約300KB |

上限は**それぞれ別に数える**。記録の登録画面では、商品の写真を5枚まで、
同時に登録するメニュー写真を10枚まで選べる。

メニューは文字を読む必要があるため解像度を上げる。複数ページにわたることがあるため枚数も多くする。

**店の写真を1人1枚に制限する理由**

店の写真は、店一覧のサムネイルと店の詳細のヘッダーに**最新の1枚だけ**が使われる。
古いものは表示されないため、溜めても容量を消費するだけになる。

撮り直した場合は**その人自身の前の写真と差し替える**。他人の写真は削除しない
（削除できるのは撮影者と管理者のみ、というルールを守るため）。
結果として、店ごとの外観写真は「その店に関わったユーザー数」が上限になる。

**登録の入口**

いずれの種類も、以下の3つから登録できる。

| 入口 | 使う場面 | 店の指定 | 撮影日の既定値 |
|---|---|---|---|
| 記録の登録画面で種類を選ぶ | 食事と一緒に撮ったとき | 記録から自動 | `records.eaten_on` |
| 店の詳細の「＋ 追加」 | 登録済みの店で撮ったとき | 画面から自動 | 当日 |
| 店一覧の「＋」 | **新しい店で撮ったとき** | **画面内で選ぶ／新規登録する** | 当日 |

3つ目では、店の選択欄で既存の店を選ぶことも、Google Places から新しく登録することもできる。
店の登録と写真の登録を1つの画面で完了できるため、2段階を踏まなくてよい。

店の選択欄は記録の登録画面と同じ部品を使う（既存店のサジェスト → Places 検索 → 店名の確認 → 正規化）。

**時系列の蓄積**

同じ店で撮り直すたびに時系列で溜まり、店の詳細では新しい順に並ぶ。
これにより、**メニュー改定や価格改定を後から比較できる**。
制覇率を廃止したため「その店に何があるか」を知る手段がなかったが、メニュー写真がその役割を担う。

**削除の権限と実行経路**

店の写真を削除できるのは**撮影した本人と管理者のみ**。
`shops` は全ユーザー共有のため、他人が撮った写真を勝手に消せないようにする。

ただし**管理者かどうかは MySQL の `users.role` で判定する**ため、
Supabase Storage のアクセス制御（RLS）だけでは判定できない。Supabase は MySQL を参照できない。
そこで、削除する人によって実行経路を分ける。

| 削除する人 | 経路 | 判定の方法 |
|---|---|---|
| 撮影者本人 | ブラウザから Supabase Storage へ直接 | Storage のポリシーで `auth.uid()` と `shop_photos.user_id` を照合 |
| **管理者** | **Spring Boot 経由** | Spring Boot が MySQL の `users.role` を確認し、サーバー側の権限で削除する |

管理者の削除に使うサーバー側の権限キー（Service Role キー）は、**ブラウザには渡さない**。
渡すと、そのキーを取得した誰もがすべての写真を削除できてしまう。
Spring Boot の環境変数として保持し、サーバー内でのみ使用する。

#### 店の編集

登録済みの店は、**店名・業態・エリア**を編集できる。支店名を消し忘れた、業態を間違えた、
といった修正のために必要になる。

**編集できる人**

`shops` は全ユーザー共有だが、**編集は全ユーザーに許可する**。
商品の分類変更と同じ理由で、管理者に限定すると誤りを見つけても直せず運用が滞るため。

**店名を変更したときの扱い**

`UNIQUE (shop_name, area_id)` があるため、変更後の名前が同一エリアの既存店と重複する場合は
**エラーとして拒否する**。自動で統合すると、別々の店の記録が混ざってしまうため。

店の統合機能はスコープ外とする（商品の統合機能と同じ理由）。

**削除はしない。閉店はフラグで扱う**

店には他ユーザーの記録も紐づくため、MVP では店の削除機能を設けない。
閉店した店は `shops.is_closed` を立てて扱い、過去の記録は残したまま新しい記録の対象から外す。

| 場面 | 閉店した店の扱い |
|---|---|
| 店一覧 | 表示する（「閉店」バッジを付け、末尾にまとめる） |
| 記録・写真の登録での店の選択 | **候補に出さない** |
| 検索の「まだ食べていない」 | **除外する**（もう食べられないため） |
| 過去の記録・写真 | そのまま残す |

閉店の入力も全ユーザーができる。誤って閉店にされた場合は、同じ画面で戻せる。

#### 画像アップロードとデータの整合性

画像を Supabase Storage にアップロードした後で DB の登録に失敗すると、
どこからも参照されない「孤児ファイル」が残る。2段構えで対処する。

| 対策 | 内容 |
|---|---|
| 即時の補償処理 | `records`・`record_photos`・`shop_photos` の登録に失敗した場合、アップロード済みの画像をすべて削除する |
| 日次のバッチ | 補償処理自体が失敗した場合に備え、参照されていない画像を定期的に削除する |

**Storage の置き場所を種類ごとに分ける**

写真は2つのテーブル（`record_photos` と `shop_photos`）に分かれて記録されるため、
Storage 上の置き場所も分ける。分けないと、片方のテーブルだけを見たバッチが
もう片方の正常な写真を「未参照」と判定して削除してしまう。

```
records/{record_id}/{ファイル名}   商品の写真   → record_photos が参照
shops/{shop_id}/{ファイル名}       メニュー・店の写真 → shop_photos が参照
```

**バッチの削除条件**

| 走査するパス | 参照を確認するテーブル |
|---|---|
| `records/` 配下 | `record_photos.photo_url` |
| `shops/` 配下 | `shop_photos.photo_url` |

いずれも「参照されていない」かつ「**作成から24時間以上経過している**」ものだけを削除する。
猶予を設けないと、アップロード直後でまだ DB の登録が終わっていないファイルを削除してしまう。

**記録を削除するときの手順**

MySQL のトランザクションと Supabase Storage への操作は、**1つのトランザクションにできない**。
別サービスへのAPI呼び出しであり、失敗しても取り消せないため。したがって順序を定める。

1. MySQL 内で `records`・`record_photos`・`likes`・`comments` を**トランザクションで削除**する
2. **コミットが成功してから** `records/{record_id}/` 配下の写真を Storage から削除する
3. 手順2が失敗した場合は、日次バッチが後から回収する

先に Storage を削除すると、DB の削除が失敗したときに「記録は残っているのに写真がない」状態になる。
DB を先に確定させ、写真の削除は失敗しても後から回収できる形にする。

店の写真（`shop_photos`）は店に紐づくため、記録を削除しても消えない。

**写真を1枚だけ削除するときの手順**

記録や店を消さずに、写真を1枚だけ削除する場合も同じ順序に従う。

1. 該当する `record_photos` または `shop_photos` の行を削除する
2. コミット後に Storage のファイルを削除する
3. 失敗した場合は日次バッチが回収する

`record_photos` の代表写真（`sort_order` の先頭）を削除した場合は、
残った写真の先頭が新しい代表写真になる。

## 6. 非機能要件


| 項目    | 要件                                                                         |
| ----- | -------------------------------------------------------------------------- |
| 画像 | アップロード時にブラウザ側でリサイズ・圧縮する。Supabase Storage の無料枠が 1GB のため。**商品の写真は1記録あたり最大5枚**（WebP・長辺1200px・約150KB）、**店の写真（メニュー・外観）は1回の登録あたり最大10枚**（メニューは文字を読む必要があるため WebP・長辺1600px・約300KB） |
| 表示    | レスポンシブ対応。スマホでの記録、PCでの閲覧の両方を想定                                              |
| 認証    | Supabase Auth が発行する JWT を Spring Security で検証する                            |
| 認可    | 他ユーザーの記録は閲覧のみ可。編集・削除は本人のみ                                                  |
| Storage のアクセス制御 | 閲覧は全ユーザーに許可（全記録を公開扱いとするため）。アップロードは本人のみ。削除は本人のみブラウザから直接行い、管理者による削除は Spring Boot 経由でサーバー側の権限を使う（Service Role キーはブラウザに渡さない） |
| 外部API の利用制御 | Google Places API は従量課金のため、APIキーに参照元制限とAPI制限をかけ、Field Mask で取得項目を絞り、Autocomplete はセッショントークンを使用する。予算アラートを設定する |
| 文字コード | 絵文字を保存するため MySQL は utf8mb4 を使用                                             |
| 稼働 | Supabase の無料プランは**7日間データベースの活動が少ない**とプロジェクトが停止する。GitHub Actions の cron から**Supabase のデータベースに軽量なクエリを実行**して防ぐ（APIサーバーへのアクセスでは Supabase の活動とみなされない） |




## 7. スコープ外（あえてやらないこと）


| 項目          | 理由                                                  |
| ----------- | --------------------------------------------------- |
| 記録ごとの公開範囲設定 | MVP では全記録を公開扱いとする。カラム追加で後から対応可能なため                  |
| 実店舗単位の管理     | 店は「店名 + 都道府県」で一意とする。`place_id` による実店舗単位にすると、コンビニの商品が支店ごとに分かれ、未食判定と前回カスタムのコピーが機能しなくなるため |
| 商品の販売期間管理   | 入力の手間に見合わないため、`is_seasonal` フラグのみとする                |
| 献立の提案機能     | 提案の質を担保するのが難しく、スコープが膨らむため                           |
| フォロー機能      | タイムラインは全公開記録の新着順で成立するため                             |
| 店名変更への追従 | 店名が変わると別の店として登録される。改名は頻度が低く、追従には店舗の同一性判定が必要なため |
| 店・商品の統合機能 | 重複して登録された店や商品をまとめる機能。入力補助と正規化で発生頻度を下げることを優先する |
| 店の重複登録時の確認画面 | 同名の店が既にある場合に「同じ店か／別の店か」を確認する画面。発生頻度が低いため自動統合とする |
