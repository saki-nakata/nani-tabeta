# 技術選定の理由

## 全体構成

```
Next.js 16 (App Router)
    ↓ REST API + Bearer JWT
Spring Boot 4.0（3層 + MyBatis + Spring Security）
    ↓
MySQL 8.4 LTS
    +
Supabase Auth（Google OAuth）/ Supabase Storage（写真）
```

## バージョン

2026年9月7日〜8日、環境構築時に決定したもの。

**採用**はプロジェクトとして定めたもの、**確認値**は環境構築時に実際に動作したもの、
**管理・再現方法**はそれがどこまで固定されているかを示す。

| 対象 | 採用 | 確認値 | 管理・再現方法 |
|---|---|---|---|
| Java | 25 | Temurin 25.0.4.1 | `build.gradle` の toolchain。**バージョンのみ指定し、ベンダーは限定していない** |
| Spring Boot | 4.0.8 | 同左 | `build.gradle` のプラグインで完全固定 |
| MyBatis Spring Boot Starter | 4.0.1 | 同左 | `build.gradle` で完全固定 |
| Gradle | 9.7.1 | 同左 | Gradle Wrapper で完全固定 |
| MySQL | 8.4 系 | 8.4.11 | `docker-compose.yml` の `mysql:8.4`。**系列内のパッチ更新には追随する** |
| Next.js | 16.3.4 | 同左 | `package.json` で完全固定 |
| React / React DOM | 19.2.8 | 同左 | `package.json` で完全固定 |
| Tailwind CSS | 4 系 | 4.3.3 | `package.json` は `^4`。**再現は `pnpm-lock.yaml` による** |
| TypeScript | 5 系 | 5.9.3 | `package.json` は `^5`。**再現は `pnpm-lock.yaml` による** |
| Node.js | 20.9 以上 | 24.11.0 | Next.js 16 の最低要件。**リポジトリでは固定していない** |
| pnpm | 11.9.0 | 同左 | `package.json` の `packageManager` |

フロントエンドはいずれも導入時点の最新安定版である。Spring Boot のような
組み合わせ上の制約がなかったため、`latest` をそのまま採用している。

### Spring Boot を 4.0 系にした理由

Spring Initializr の時点では 4.1.1 が最新の安定版だったが、MyBatis を選ぶとエラーになった。

```
Requires Spring Boot >= 4.0.0 and < 4.1.0-M1
```

`mybatis-spring-boot-starter` は Spring チームではなく MyBatis 側が提供しているため、
Spring Boot の新しいマイナーバージョンへの追随に時間差がある。
**MyBatis を採用する以上、Spring Boot 側を追随済みの系列に合わせる**必要があり、
条件を満たす安定版である 4.0.8 を選んだ。開発版ではなく正式リリースのため品質上の懸念はない。

なお Spring Boot 3 系は Initializr の選択肢に残っていない。

### Java を 25 にした理由

選択肢は 26 / 25 / 21 / 17 で、このうち LTS は 25 / 21 / 17。
26 は非 LTS のため除外し、現時点で最新の LTS である 25 を採用した。

Lombok は JDK 25 上で `sun.misc.Unsafe` に関する非推奨警告を出すが、ビルドは成功する。
Lombok のようにバイトコードを操作するライブラリは新しい JDK への追随が遅れやすいため、
警告が実害に変わった場合は 21 に下げる判断もありうる。`build.gradle` の1行で切り替えられる。

### Spring Boot 4 での変更点

Spring Boot 3 までの記事や過去の学習用コードをそのまま流用できない箇所がある。

| 3 まで | 4 |
|---|---|
| `spring-boot-starter-web` | **`spring-boot-starter-webmvc`** |
| `spring-boot-starter-test`（全部入り）| 機能ごとに分割（`-webmvc-test` など）|

## なぜ Spring Boot を挟むのか

Next.js と Supabase だけでもアプリは成立する。実際、開発速度はそのほうが速い。
それでも Spring Boot を挟んだのは、**学習してきた Java をバックエンドとして使いたかった**ためである。
Java で書いたほうが、学んできた分だけ自分で理解しながら実装できると判断した。

結果として、以下がコードに現れる。Supabase のクライアントSDKを直接呼ぶ構成では書く場所がない部分である。

- 3層アーキテクチャ（Controller / Service / Repository）による責務分離
- トランザクション管理
- 業務ルールの実装（例：自分の記録にはいいねできない）
- 単体テスト（Controller / Service / Repository の各層）

## なぜ MyBatis か（JPA ではなく）

1. **スクールでの学習時に MyBatis を使っており、JPA には触れたことがなかった**ため
2. **Excel VBA を習得しており、Excel から Access のデータベースに接続してデータを読み書きする際に SQL を書いていた**ため、SQL を直接書くほうが慣れていて理解しやすい
3. 店・商品の記録閲覧では、商品ごとの記録件数と平均評価を集計する必要がある。
   また検索は店名・商品名・分類・期間を任意に組み合わせるため、動的な SQL の組み立てが必要になる。
   どちらも XMLマッパーで素直に書ける

JPA は SQL を自動生成するため単純な CRUD は簡潔になるが、生成される SQL が見えにくい。
今回は自分で理解しながら実装することを重視したため、SQL が明示される MyBatis を選んだ。

## なぜ MySQL か

スクールでの学習時に使用しており、MyBatis との組み合わせも経験済みであるため。

## なぜ Supabase Auth か

### Google OAuth だけでは足りない

Google が提供するのは「この人は誰か」という本人確認だけである。
アプリとして成立させるには、その先に以下が必要になる。

| 必要なもの | Google が提供するか |
|---|---|
| 本人確認（IDトークンの発行） | ✅ |
| 認可コードとトークンの交換 | ❌ 自前実装 |
| IDトークンの検証（署名・aud・iss・exp） | ❌ 自前実装 |
| ユーザーの作成・永続化 | ❌ 自前実装 |
| セッション管理（Cookie・有効期限） | ❌ 自前実装 |
| トークンの自動更新（IDトークンの有効期限は1時間） | ❌ 自前実装 |

Supabase Auth がこれらを肩代わりする。Google は「ログイン手段（provider）」として指定するだけになる。

```typescript
await supabase.auth.signInWithOAuth({ provider: "google" });
```

### 前プロジェクトでの実績

food-delivery-app で同じ構成を使用している。以下の1行で、トークン交換・検証・ユーザー作成・セッション発行が完了する。

```typescript
await supabase.auth.exchangeCodeForSession(code);
```

セッションの更新は middleware の `auth.getUser()` が担当する。
また Google の `client_secret` はコードにも環境変数にも存在しない。Supabase 側に登録されており、
Google とのやり取りが Supabase で完結していることを示している。

### Supabase Storage との統合

写真は Supabase Storage に保存する。ブラウザから直接アップロードするには Supabase の認証トークンが必要になる。
Supabase Auth を使わない場合、画像を Spring Boot 経由で中継することになり、APIサーバーの通信量とメモリを消費する。

### 検討した代替案

Google の IDトークンを Spring Boot に直接送り、Google の公開鍵で検証する構成も技術的には成立する。
ただしトークンの更新・セッション管理・ユーザー情報の保存をすべて自前で実装することになり、
上記の Storage の問題も残るため採用しなかった。

### 方針との整合

Spring Boot 側は **JWT を検証し、`sub`（利用者ID）を取り出す**ことだけを担当する。
検証するのは署名だけでなく、`iss`（発行者）・`aud`（宛先）・`exp`（有効期限）も含む。
Supabase は誰でもプロジェクトを作成できるため、`iss` を検証しないと、
攻撃者が自分のプロジェクトで発行した正しく署名されたトークンで認証を通過できてしまう。
認証の作り込みに時間を取られず、**認可の設計**（他ユーザーの記録は閲覧のみ、管理者だけが分類・業態を追加できる）に集中できる。
このアプリでは認可のほうが考えるべきことが多い。

## なぜ Supabase Storage か

### 認証と統合されている

写真はブラウザから Supabase Storage へ直接アップロードする。
このとき **Supabase Auth のログイン状態がそのまま使える**ため、
「このユーザーはアップロードしてよいか」の判定を自前で実装する必要がない。

Supabase Storage のアクセス制御は「ポリシー」として記述し、
その中で**ログイン中のユーザーIDを直接参照できる**。

```sql
-- 「自分のフォルダにだけアップロードできる」というポリシー
create policy "own upload"
on storage.objects for insert
to authenticated
with check ( (storage.foldername(name))[1] = auth.uid()::text );
                                              ↑ ログイン中のユーザーID
```

認証とストレージが同じサービスの中にあるため、この参照が成立する。

### Google Cloud Storage ではない理由

写真の保存先の候補として、無料枠が 5GB と大きい Google Cloud Storage も検討した
（Supabase Storage は 1GB なので、容量だけを見れば5倍で有利）。

採用しなかった理由は、**前項の利点である「ログイン状態がそのまま使える」が失われる**ことである。
Google のログインと Google Cloud Storage は、同じ会社のサービスだが別系統の仕組みであり、
ログイン情報を Storage の権限判定に使えない。

| | 何のための仕組みか | 誰を識別するか |
|---|---|---|
| Google OAuth（ログイン） | 一般ユーザーの本人確認 | **アプリを使う人** |
| Google Cloud Storage | GCP というクラウドサービスの一部 | **GCP を契約している開発者** |

Cloud Storage の権限管理（IAM）は、クラウドを契約している開発者やサーバー向けの仕組みであり、
「アプリにログインしてきた一般ユーザー」を識別する用途には使えない。
そのため、ユーザーが Google でログインしても、そのトークンで Cloud Storage にはアクセスできない。

結果として、次の実装が必要になる。

```
ブラウザ「この画像をアップロードしたい」
      ↓
Spring Boot が「署名付きURL」を発行
      ※ 署名付きURL＝一時的にアップロードを許可する、期限つきの専用URL
      ↓
ブラウザがそのURLへアップロード
```

これは AWS S3 を使う場合とまったく同じ手間である。
Supabase Storage なら、ログイン済みのブラウザがそのままアップロードできるため、この処理自体が不要になる。

### 無料枠の制約

| サービス | 無料枠 | 制約 |
|---|---|---|
| Supabase Storage | 1GB（期限なし） | 容量が小さい |
| Google Cloud Storage | 5GB/月（期限なし） | **us-east1 / us-west1 / us-central1 に限定**。東京リージョンは課金対象。請求先アカウントの登録が必須 |
| AWS S3 | 2025年7月15日以降に作成したアカウントは、Free プランで**最長6ヶ月**またはクレジット（$100〜$200）を使い切るまで。それ以前のアカウントは従来どおり12ヶ月 | 期限がある |

Google Cloud Storage は容量では有利だが、無料枠が**米国リージョン限定**のため、日本からのアクセスは遅くなる。
写真の表示速度に直結するため、この構成では採用しない。

### 容量の制約と対策

無料枠は 1GB。スマホの写真をそのまま保存すると約340枚で上限に達するため、
**アップロード時にブラウザ側でリサイズ・圧縮する**（WebP・長辺1200px で約150KB、約6,800枚相当）。

なお Supabase Storage は S3互換APIを提供しているため、容量が不足した場合の S3 への移行は比較的容易である。

既習範囲を土台にしているが、以下は今回初めて扱った。

| 内容 | 実際にやったこと |
|---|---|
| **Docker Compose** | `image` / `ports` / `environment` だけの最小構成から始め、必要なものを1つずつ足した |

それが公開リポジトリに含まれてしまった。今回はその再発を防ぐ構成にしている。

## 絵文字の表示（Twemoji）

分類と業態には絵文字を持たせるが、絵文字の見た目は OS ごとに異なる。
同じ 🍰 でも Windows / macOS / iOS / Android で別のデザインになるため、
ポートフォリオとしてスクリーンショットを載せる際に環境依存の差が出る。

これを避けるため、フロントエンドで **Twemoji**（`@twemoji/api`）を使い、
表示時に絵文字を SVG 画像へ置き換える。

DB の設計には影響しない。`category_emoji` には Unicode の絵文字をそのまま保存し、
画像への変換は表示の瞬間にのみ行う。

なお、旧来の `twemoji` パッケージは 2022年6月で更新が止まっている。
現行は `@twemoji/api` であるため、導入時はこちらを使う。

## デプロイ構成

| 対象 | サービス |
|---|---|
| Next.js | Vercel（Hobby プラン） |
| Spring Boot / MySQL 8.4 | Railway |
| 認証・写真 | Supabase |

Spring Boot と MySQL は、**同一プラットフォーム内の別サービス**として配置し、
内部ネットワークで接続する。MySQL は外部に公開しない。

```
Railway Project
├─ Spring Boot Service
└─ MySQL Service（Docker イメージ mysql:8.4）
```

### なぜ Railway か

| 条件 | Railway |
|---|---|
| 初回アクセスを待たせない | **Serverless を明示的に有効にしない限り常時起動する**ため、コールドスタートが発生しない |
| メモリの安全マージン | **実際に消費した CPU・メモリに応じた課金**。上限を高めに設定しても、使わなかった分は課金されない |
| MySQL の非公開 | Private Networking で内部接続する |
| MySQL 8.4 | Docker イメージ（`mysql:8.4`）を指定できる |
| 管理 | ブラウザのGUIで完結。ログ・メトリクスの確認や再起動も画面上で行える |

「タイムアウトのリスクを下げるためメモリに余裕を持たせたい」という方針に対し、
**上限に安全マージンを設定しても未使用分が課金されない**ことが決め手となった。

なお「デフォルトが常時起動」という性質は、**可用性の面で今回の要件（採用担当者の初回アクセスを
待たせない）に合致する**という意味であり、費用面では常に課金され続けることを意味する。

### 費用の試算

Railway は実使用量による課金のため、事前に確定額を出すことはできない。
Railway 自身も、アプリごとに異なるため正確な事前見積もりはできないと説明している。

Spring Boot と MySQL がそれぞれ平均 400MB 前後、CPU 使用量が小さいと仮定した場合：

| 項目 | 概算 |
|---|---|
| メモリ 約0.8GB × 約$10/GB | 約 $8 |
| CPU（アイドル中心） | 約 $1 |
| 合計 | **月 約$9（約1,350円）** |

ここに Volume・ネットワーク送信量・バックアップ容量が加わる。
**実際の費用はデプロイ後のメトリクスで検証する。**

### Fly.io との比較

最後まで比較したのは Fly.io である。構成としてはどちらでも実現できる。

| | Fly.io | Railway |
|---|---|---|
| Spring Boot と MySQL を同一プラットフォーム内の別サービスとして配置 | ✅ | ✅ |
| MySQL を内部ネットワークで接続 | ✅ | ✅ |
| MySQL 8.4 の Docker イメージ指定 | ✅ | ✅ |
| HTTPS の自動対応 | ✅ | ✅ |

差が出るのは、**課金方式**と**デフォルトの挙動**の2点である。

#### 違い①：課金方式

| | 課金の対象 |
|---|---|
| Fly.io | **確保した Machine のサイズ**。使わなくても全額課金される |
| Railway | **実際に消費した CPU・メモリ**。上限を設定しても、使わなかった分は課金されない |

Fly.io 東京リージョン（nrt）の shared-cpu-1x は 512MB が $4.05/月、1GB が $7.23/月、
Volume が $0.15/GB/月（$1 = 150円で換算）。

| 構成 | Fly.io 東京 | Railway（試算） |
|---|---|---|
| 512MB × 2 + Volume 1GB | 約 $8.3（約1,250円） | 約 $9（約1,350円） |
| **1GB × 2 + Volume 1GB** | **約 $14.6（約2,200円）** | **約 $9（約1,350円）** |

512MB 構成では両者ほぼ同額である。しかし **Spring Boot・MySQL のいずれも 512MB では余裕が少なく、
安定して公開する構成としては選びにくい**。1GB に上げると Fly.io は費用が倍近くになるのに対し、
Railway は実使用量が変わらなければ費用も変わらない。

ただし Railway でも、メモリリークなどで実使用量が増えればその分は課金される。
「余裕分が完全に無料」ではなく「**使わなかった余裕分は課金されない**」が正確である。

#### 違い②：デフォルトの挙動

| | デフォルト | 常時起動にするには |
|---|---|---|
| Fly.io | **アイドル時に Machine を停止する** | `fly.toml` で `auto_stop_machines = "off"` |
| Railway | **常時起動** | 変更不要 |

Fly.io で自動停止が有効な場合、**Machine が停止した後の最初のリクエスト**で
Spring Boot の起動待ちが発生する。起動後のリクエストでは発生しない。

#### Fly.io が勝っている点

**東京リージョンを選択できること。** Railway は Singapore が最寄りで、API レスポンスに差が出る。

写真本体は Supabase Storage / CDN から直接配信されるため転送への影響は限定的だが、
**画像URLを含む記録情報は Spring Boot の API から取得するため、API の遅延は画像の表示開始にも影響する。**
この点を許容したうえで Railway を選んでいる。

### 検討したが採用しなかったデプロイ先

| 候補 | 不採用の理由 |
|---|---|
| AWS（EC2 + RDS など、APIサーバーとDBを分離する構成） | 費用が上回るうえ、OSのセキュリティ更新・ネットワーク設定・HTTPS対応（ドメイン取得 + Nginx + Let's Encrypt）がすべて必要で運用負荷が高い |
| Fly.io | 東京リージョンは優れるが、確保サイズ課金かつデフォルトで自動停止するため（詳細は前項） |
| Google Cloud Run | 無料枠は大きいが、常時起動（`min-instances=1`）にすると割高になり優位性が消える |
| Oracle Cloud Always Free | 無料だが、7日間の平均でCPU・ネットワーク使用率が10%未満だとインスタンスが停止される |
| Koyeb | 無料の Web Service では永続ボリュームが使えず、Database Service も MySQL に対応していない。MySQL を動かす手段がない |

なお、単一の VM に Spring Boot と MySQL を同居させる構成（AWS Lightsail など）は月$12程度で、
Fly.io 東京の 1GB × 2 より安くなる場合がある。「AWSより安い」と一般化することはできず、
**APIサーバーとDBを分離する構成と比べて安い**というのが正確である。

### 運用時の設定

- Railway の **Usage Limit** を設定する。ただしこれは請求額のみを固定する機能ではなく、
  上限に到達するとワークロードが停止する。**予算超過を防げる代わりに、
  上限到達時のサービス停止を許容する必要がある。**
- Supabase のプロジェクトは**東京リージョンで作成する**（未実施）
- GitHub Actions の cron から Supabase のデータベースに軽量なクエリを実行し、自動停止を防ぐ
